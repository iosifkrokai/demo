## 1. Решение по архитектуре: два шелла, десктоп заморожен

**Вариант A — продолжать заплатки `max-md:` (отвергнут).** Десктопные компоненты уже перегружены условными классами: `sidebar.tsx` 2282 строки, из них заметная часть — мобильные исключения; каждое новое правило ломает что-то в соседнем. Это и есть источник обеих жалоб.

**Вариант B — два шелла, один переключатель (выбран).**
- Десктопная ветка (текущие `sidebar.tsx`, `map/index.tsx` и `parts/`) **не трогается вообще** — она остаётся эталоном и остаётся под своими спеками.
- Мобильная ветка — новые компоненты в `frontend/src/components/mobile/`, собранные «под палец», а не «под курсор».
- Логика (запрос, фильтры, планирование, сессия проводника, гео-фикс, сервисы по пути) выносится в **хуки** и живёт одна на оба шелла; сторы Zustand уже общие.
- Точка переключения одна: `app.tsx` рендерит `MobileShell` при `max-width: 767px`, иначе текущую связку. Больше нигде `matchMedia`/`max-md:` в мобильном слое не используется.
- Примитивы (`Chip`, `Button`, `ToolButton`, `Sheet`) получают **вариант плотности** (`size="compact"`/`density`), а не наследуют `max-md:`-грязь.

**Вариант C — перевести всё дерево на mobile-first классы (отвергнут).** Требует переписать десктоп, а он заморожен заказчиком; риск регрессий в единственной ветке, которая сейчас работает.

Почему B отвечает на жалобы: «слишком большое» лечится новыми плотными мобильными компонентами, а не подкруткой десктопных; «перекрывает карту» — тем, что хром карты проектируется отдельно, с бюджетом площади.

## 4. Замер как часть работы: `scripts/measure-mobile.mjs`

Скрипт (по образцу моих прогонов через CDP) открывает стенд на 390×844 и на 1440×900 и печатает таблицу «порог / факт / PASS|FAIL»:

1. доля видимой карты и высота панели в каждом состоянии (планирование / результат / ведение);
2. площадь плавающего хрома карты в % от видимой карты;
3. минимальная мишень по меньшей стороне среди всех кнопок панели и карты;
4. наличие главного действия без прокрутки (кнопка внутри видимой области панели);
5. окно прокрутки формы (>= 2 строк содержимого);
6. перекрытия пар элементов (кнопки между собой, плашка места, столбец карты);
7. горизонтальное переполнение документа (должно быть 0);
8. десктоп 1440×900: панель 420 px, ширина/высота панели, отсутствие изменений относительно эталона.

Пороги — из §F2–F3 спеки. Скрипт запускается после каждой фазы; его вывод прикладывается к коммиту. Тот же принцип, что и раньше: **решение принимается замером, а не мнением**.

## 5. Фазы и гейты

Каждая фаза: отдельный коммит, свой замер, гейты из §6. Оценка — в днях одной руки; при делегировании Claude Code фаза дробится на куски по паре файлов (см. §7).

- **Ф0. Каркас замера и basline (0.5 д).** `scripts/measure-mobile.mjs`, зафиксированные числа сегодняшнего состояния в `plan.md` (уже есть) и в выводе скрипта. Гейт: скрипт печатает те же числа, что в §0 ±2 px.
- **Ф1. Шелл и переключатель (1 д).** `use-is-mobile`, `mobile-shell` (карта + панель + докнутая кнопка), панель в трёх состояниях, пока без нового содержимого — те же разделы, что сегодня, но в мобильной компоновке. Гейт: карта ≥ 62 % в покое, главное действие без прокрутки, десктопный замер не изменился, десктопные спеки без правок зелёные.
- **Ф2. Плотность (1.5 д).** Токены `density.ts`, компактные варианты примитивов, перенос табло/поля/чипов/RU-EN. Гейт: ни одна мишень < 40 px, окно формы ≥ 2 строк, лист ≤ 38dvh.
- **Ф3. Планирование (1 д).** Подсказки строкой, секции-аккордеон, пресеты времени и транспорт на первом экране, фильтры в шторке. Гейт: в состоянии покоя видны поле, подсказки, время, транспорт и кнопка; прокрутка только внутри панели.
- **Ф4. Результат маршрута (1 д).** Полоса ≤ 132 px (длина, время, число остановок, «Пойти», «Подробнее»), список остановок в полном состоянии. Гейт: карта ≥ 72 %.
- **Ф5. Хром карты (1 д).** Столбец 44 px, пилюля-сводка, плашка места одной строкой с автоскрытием. Гейт: хром ≤ 8 % площади видимой карты, перекрытий нет.
- **Ф6. Проводник (0.5 д).** Перенос уже сделанного ведения (курс, склейка маневров, крупное расстояние, подсказка «рядом», голос) в `mobile-guide-strip`. Гейт: карта ≥ 66 %, «вход в проводник сразу ведёт», баннер читается с телефона.
- **Ф7. Полировка и документы (1 д).** Пустые/ошибочные состояния, фокус и клавиатура, автоскрытие элементов, обновление `frontend/DESIGN.md` разделом о мобильной плотности, финальный замер-отчёт в коммите. Гейт: все пороги PASS, десктоп без изменений.

Итого ≈ 8 дней; на стенде после каждой фазы рабочее состояние, откат — по коммиту.

## 6. Гейты приёмки (одинаковые для каждой фазы)

- **A1 Код:** `npm run typecheck` 0; названные спеки зелёные; линт по изменённым файлам без новых проблем относительно baseline (6).
- **A2 Мобильный замер:** пороги фазы PASS на 390×844.
- **A3 Десктоп:** замер 1440×900 совпадает с эталоном (панель 420 px, порядок блоков, подсказки переносятся) и десктопные спеки зелёные **без правок**.
- **A4 Палец:** ни одной мишени < 40 px; прокрутка только внутри панели; горизонтального переполнения нет.
- **A5 Язык:** паритет ru/en зелёный, все новые строки через `t()`.
- **A6 Скриншоты:** приложены к коммиту (390×844 по состояниям + 1440×900), и они совпадают с числами замера.

## 7. Порядок исполнения и роли

- Исполнитель — Claude Code отдельными фазами/кусками (по паре файлов на задание), проверка — моя: типы, названные спеки, сборка, живой замер, десктопный эталон.
- Причина дробления: длинные задачи Клода падают на 5-часовом окне **посередине** и оставляют некомпилируемое дерево (дважды за сегодня). Поэтому: задание ≤ одному куску, после каждого — коммит; при обрыве — `git diff > partial.patch`, откат до зелёного, продолжение с патча.
- Заказчик проверяет на телефоне после каждой фазы; замечания принимаются как «ощущение» и переводятся в числа замера перед правкой.

## 8. Риски и как снимаются

| Риск | Снятие |
| --- | --- |
| Дублирование разметки в двух шеллах | логика в хуках, примитивы с вариантом плотности, мобильные компоненты только про раскладку |
| Дрейф поведения между шеллами | общие сторы + контрактные тесты на вынесенные хуки (не на разметку) |
| Регрессия десктопа | гейт A3: замер + десктопные спеки без правок |
| Рост бандла от второго шелла | дерево шейпится по брейкпоинту; следим за размером `npm run build` (порог: +0 новых зависимостей, рост ≤ 5 %) |
| «Плотность» уронит доступность | правило §3 (≥ 40 px, вторая сторона ≥ 64), проверка фокуса, замер мишеней в скрипте |
| Обрыв агента на лимите | дробление, коммит после каждой фазы, патч+откат |
| Спор «красиво/некрасиво» | только замер с порогами; ощущения заказчика переводим в числа |
