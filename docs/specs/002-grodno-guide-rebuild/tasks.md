## W14 — Уточнение маршрута: найдено живой проверкой (owner: Hermes, в работе)

Репорт пользователя: «попросил отсортировать точки маршрута по времени нахождения в точке — агент выдал
чушь». Воспроизведено на живом стеке (`POST /routes/generate`, тот же запрос, что строит базовый
маршрут, плюс `context.instruction` и `base_points`):

| Инструкция | Что вернул бэкенд |
| --- | --- |
| «Отсортируй точки маршрута по времени нахождения в точке» | **HTTP 422** `{"detail":"optimizer could not produce a route with ≥ 2 stops"}` — базовые точки не выживают, хотя их три |
| «Поменяй порядок остановок: сначала те, где нужно больше времени» | инструкция **молча проигнорирована**: базовые остановки выброшены, собран другой маршрут (Мештовичи, Каменные могилы, Жерно, Аграсядзіба — область вместо старого города), в `changes` только `added` |

Вывод: **предел не в модели, а в наборе операций.** В плане нет операции «переупорядочить по признаку»,
и неизвестная инструкция приводит не к честному отказу, а к перепланированию с нуля — то есть к тому
самому «выдал чушь». Требуется: (1) уточнение сохраняет базовые остановки, если не просили добавить/
убрать; (2) явная переупорядочка по признаку (время осмотра, расстояние от старта); (3) инструкция, для
которой операции нет, возвращает код причины «не поддерживается» и не трогает прежний маршрут.

- [ ] Уточнение не заменяет маршрут молча: базовые точки сохраняются, изменение отражается в `changes`.
- [ ] Переупорядочка по времени осмотра и по расстоянию от старта реализована и покрыта тестами.
- [ ] Неподдерживаемая инструкция → код причины + короткий текст, прежний маршрут без изменений.
- [ ] 422 на пути уточнения устранён; тест, что `base_points` доживают до оптимизатора.
